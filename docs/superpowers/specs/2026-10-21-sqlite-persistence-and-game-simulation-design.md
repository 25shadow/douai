# SQLite 持久化与游戏模拟选择设计

## 目标

让 SQLite 成为项目持久配置的唯一来源，同时让模拟直播由用户明确选择游戏后启动，未连接或未模拟时维持无直播、无运行游戏的状态。现有游戏逻辑、DyCast 连接及弹幕转发行为保持不变。

## 当前情况

- `config_server.py` 已通过 SQLite 保存直播房间号、转发地址、运行行为、语音设置、问答配置和 AI 配置。
- `src/services/configApi.ts` 仍将房间号和转发地址写入 `localStorage`，并在 API 不可用时静默使用前端默认配置。
- 模拟直播参数保存在 `localStorage`。
- DyCast `sessionid` 作为浏览器 Cookie 保存，连接逻辑读取该 Cookie。
- 实时直播状态和跨页面模拟状态是运行时数据，不是持久配置。
- 模拟启动当前自动启动知识问答；OBS 画面在空闲时也显示默认问答预览。

## 设计

### 持久配置

继续由 `config_server.py` 作为 SQLite 的唯一读写入口。将模拟时长、初始观众数、互动间隔和现有语音前缀输入加入 SQLite 配置记录；现有配置结构和 UI 使用方式尽量保持不变。前端的 `loadConfig`、`saveConfig` 统一经由 API，服务不可用或失败时返回可见错误，不回退写入浏览器存储。

旧浏览器键 `douai-room-id`、`douai-relay-url` 和 `douai-live-simulation-config` 通过一次性迁移接口交给后端。后端只在相应 SQLite 值为空或仍为默认值时迁移旧值，使用事务写入并返回最终配置。只有收到成功响应后，前端才清理成功迁移的旧键；失败则保留旧值供重试。SQLite 已有非默认值始终优先。

`sessionid`、DyCast 必需 Cookie 保持浏览器 Cookie 存储，因为这是现有连接认证流程的一部分，迁入 SQLite 会改变安全和连接边界。直播统计、评论事件和模拟同步快照是易失运行态，不持久化。

### 游戏模拟

“模拟直播”先打开选择流程。当前列表只显示已实现的知识问答；选择游戏和配置模拟参数后，由用户明确点击开始。启动所选游戏并开始模拟直播，结束模拟时只停止本次由模拟启动的游戏，并恢复模拟前状态。独立的游戏配置与手动启动/关闭行为不变。

未连接、未模拟时，控制台和 OBS 预览呈现待开播/空闲状态，不显示正在运行的默认题目。真实直播连接及真实游戏启动时仍显示对应实时内容。模拟事件只喂给本地游戏/预览，不进入 DyCast 或 WS 转发路径。

## 错误处理

- 配置读写 API 失败时向用户显示错误，不静默成功、不用 localStorage 覆盖数据库状态。
- 迁移失败不删除任何旧键。
- 已有 SQLite 配置不被旧 localStorage 覆盖。
- 当前仅一个游戏可选时，选择 UI 明确展示知识问答；后续新增游戏按独立游戏模块注册，不添加虚构选项。

## 验收标准

1. 首次启动能将旧房间号、转发地址和模拟参数迁移到 SQLite，迁移后重启仍读取同值。
2. SQLite 已配置值优先，旧数据不覆盖；迁移成功后才清理旧键。
3. SQLite API 不可用时，读写操作明确失败，浏览器存储不被当作已保存结果。
4. 模拟启动前要求选择已实现游戏；空闲状态不自动启动游戏或显示模拟直播。
5. 选择知识问答开始模拟后，控制台与 OBS 输出持续同步游戏和模拟事件；结束后两者回到空闲状态。
6. DyCast Cookie、房间连接、WS 转发、题库与游戏独立配置/操作保持现有行为。

## 测试策略

- Python `unittest` 使用临时 SQLite 文件覆盖默认配置、迁移、已有值优先和迁移重复调用。
- TypeScript 单元测试覆盖配置/API 错误及模拟游戏选择的校验/映射。
- 浏览器验证旧数据迁移后刷新仍保留、选择游戏再启动、空闲 OBS 状态及停止恢复。
- 执行 `pnpm test`、Python 单测、`pnpm type-check` 和 `pnpm build`。
